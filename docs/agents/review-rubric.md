# 审查尺度（review rubric）

这份文档是审查者（人或模型）在本仓库提出意见时共用的尺子。`scripts/pr_review.py`
把它作为 system prompt 喂给模型；人工审查也按同一顺序读，这样两边报出来的东西
可以互相对照，模型报的不会被当成结论，人报的也不会重复劳动。

## 分工：确定性与判断

| 类型 | 谁负责 | 例子 |
| --- | --- | --- |
| 从源码文本就能判定的 | `scripts/review_gates.py`（RG001–RG003） | 事务块内搬移大文件、e2e 里的 `pytest.skip`、文档里的绝对完成声明 |
| 需要读懂意图的 | 人或模型 | 「这个闸门被去掉是有意的吗」「这条证据会不会被误读成已认证」 |
| 需要跑起来的 | 人或 CI | 真实 Docker 路径、并发下的事务表现 |

模型审查**不要**重复确定性门的结论；指出来源让它去查即可。

## 读的顺序

1. **摄入与并发**：上传、解包、发现三条路径的准入是否一致；谁在持锁做 IO；超时与预算是否覆盖全部入口。
2. **隔离边界**：容器参数、挂载、输入副本与摘要复核；失败路径是否也能收尾。
3. **证据语义**：什么算事实、什么算线索；截断是否有显式说明；状态值是否会让人读成「已确认」。
4. **契约**：schema 与生成物是否逐项对应；改动是**新增**还是**收紧**既有定义；枚举扩宽要单独点出。
5. **测试可证伪性**：这条断言删掉实现会不会红？`skip`/`xfail`/`in`/`or` 是否让用例恒真？

## 每条意见必须带

- 严重度：`P1`（会造成越权、数据损坏或证据结论错误）／`P2`（合并前应处理）／`P3`（可随手修）。
- 位置：`path/to/file.py:123`，函数名。
- 证据：引用触发问题的**那一行**原文，不要只描述。
- 触发路径：什么样的输入/时序会走到这里。
- 一句话修法。

## 必须显式声明的三件事

- **没验证的部分**：跑不了的环境（Docker、PostgreSQL、真实 APK）要说清「未验证」，不要用「应该没问题」代替。
- **已核实为干净的部分**：列出来，让人知道哪块不必回头再查。
- **事实 / 声明 / 推断**：引用代码行为是事实，作者自述是声明，推测是推断，三者不要混在一句话里。

## 禁止

- 替维护者做合并、发布、部署的决定（AGENTS.md：这些不包含在「通过验收」里）。
- 把 `TEST_READY` 一类自述文档当成验收证据。
- 因为「测试全绿」就判定可合并——先问这些测试能不能证伪。
- 只报问题不给位置，或者给位置不给证据。
