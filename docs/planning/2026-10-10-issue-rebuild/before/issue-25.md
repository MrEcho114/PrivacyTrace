- **所属阶段**：[S2 #4](https://github.com/MrEcho114/PrivacyTrace/issues/4)
- **角色分工**：C 负责编写评测脚本与运行实验，A 与 B 负责真值构建与结果核验
- **建议完成日期**：2026-10-16
- **优先级**：必做
- **前置依赖**：[PT-902 #16](https://github.com/MrEcho114/PrivacyTrace/issues/16), [PT-901 #15](https://github.com/MrEcho114/PrivacyTrace/issues/15)

### 为什么做
客观评估系统各模块的真实表现，不提前预设优势。在相同输入、相同候选证据范围和独立真值下，对比本方案与基线方案的差异，以严谨的数学标准记录各项指标、误差分布与系统开销，为答辩与报告提供可复查的事实依据。

### 做什么（输入与输出）
- **输入**：[PT-902 #16](https://github.com/MrEcho114/PrivacyTrace/issues/16) 的受控场景、[PT-901 #15](https://github.com/MrEcho114/PrivacyTrace/issues/15) 的真实样本；预先独立固化的人工真值（Ground Truth）与测试集留出策略（避免同模板导致数据泄漏）。
- **输出**：
  1. 实施 3 组方案在同等条件下的横向比对：
     - 基线 1（权限+关键词）：仅依据 Manifest 声明权限与政策全文中的数据类型关键词做粗粒度匹配；
     - 基线 2（API+扁平匹配）：使用与本系统完整方案**完全相同**的 APK/DEX 候选证据及**相同正确**的 API 完整方法描述符，仅将政策类型比对简化为扁平文本名义匹配，不包含上位分类层级、覆盖门槛、降级状态机与人工复核机制（严禁故意不校验描述符来人为制造弱基线）；
     - 方案 3（本系统完整链路）：代码证据严格映射 + 规则状态机（含 6 状态、否定/条件处理与降级保护）+ 人工复核交互；
  2. 评测维度专项拆解：
     - 证据检出与映射：评估敏感调用点（类名、方法描述符、指令偏移）提取与规则映射的准确度；
     - 政策条款抽取评估：对人工结构化条款，分别评估数据类型（data_type）、否定修饰（polarity）与限定条件（condition）的标注一致性与覆盖情况，不把本期未实际实施的大模型抽取硬塞为必测项；
     - 判定状态混淆矩阵：按各对照状态（如 EXACT_MATCH、CATEGORY_MATCH、NOT_DECLARED、INSUFFICIENT_EVIDENCE 等）分别统计混淆矩阵；
  3. 指标数学标准与开销记录：
     - 严格遵循标准数学公式：Precision = TP / (TP + FP)，Recall = TP / (TP + FN)，F1 = 2 * Precision * Recall / (Precision + Recall)；零分母统一标注为 N/A；
     - 异常样本口径处理：失败、partial 与弃判样本不随意加为传统 P/R 分母中的 FP，必须保留在全样本的“覆盖率”、“解析成功率”与“弃判率”统计分母中，并明确说明如何计入各个可测目标的漏报（FN）或归为不可测状态，严禁悄悄删除困难样本；
     - 算法自动给出的候选结果与人工修正后的最终结果分列两组独立统计；
     - 受控真值按可测目标计数；对商业闭源 App，明确指出代码全局真实行为在客观上不可测，不虚构召回率；
     - 记录端到端分析耗时、内存峰值与人工复核时间。

### 完成标准（验收证据）
- 生成自动化评测脚本与输出报表（Markdown 与 JSON 格式），计算公式与分母口径完全符合数学规范；
- 报表数据全部来自真实运行统计，无测试数据前不写任何“提升”结论，零分母如实标注 N/A；
- 混淆矩阵与全样本覆盖率指标自洽，困难样本、失败样本有清晰留痕；
- 实验所用的输入哈希、规则版本与运行环境参数清晰记入报告。

### 怎么检查（验证计划）
- 运行基准测试 runner 脚本，验证能否自动跑完全部对比用例并导出统计文件；
- 检查基线 2 的实现代码，确认其使用了与方案 3 相同的完整方法描述符与解析输入；
- 抽查受控场景的人工真值，核对 TP/FP/FN 与计算出的 Precision/Recall/F1 数值；
- 核实困难样本未被剔除，分母统计口径无误。
