# PrivacyTrace 开发方案调研与收敛建议

日期：2026-10-03（Asia/Shanghai）。状态：建议稿，未冻结需求，未开始功能开发。

## 0. 先给结论

**值得继续，但不应做“万能隐私测谎仪”。建议做“Android 隐私声明证据核验与复核工作台”：帮助普通用户看懂可观察的静态线索，帮助团队复核这些线索在指定版本的政策中是否有对应声明。**

现有 Vue/FastAPI 骨架可以保留。第一版的核心不是大图、LLM 长篇总结或完整污点分析，而是：

1. **真实 APK 的可定位证据**：权限能力、敏感 API 调用点、有限 SDK 存在线索，并显示分析未覆盖区域。
2. **中文政策的可审阅声明**：原句、否定/条件、来源、适用版本、人工修订与抽取失败记录。
3. **谨慎且可复核的核验结果**：按独立政策来源对照，区分匹配、粒度不足、候选缺失与证据不足，任何结论能返回依据。

这属于有实质开发工作的工程产品化方向，不应承诺论文级首创或保证获奖。闭源国产 APK 是实际分析对象；开源、自建 APK 是建立可验证真值的手段，第一版不另做完整 Repo 分析产品。

**排期约束比技术栈更重要：官网当前通知写明 2026-10-23 23:59:59 截止报名及作品提交。按今天算仅约 20 天；校内期限可能更早。** 用户称 5 人团队，其中一人挂名、一人不熟技术；以下暂按这两人在 5 人之内、约 3 个编码位 + 1 个非技术执行位制定，不将挂名者计入产能。[赛事官方通知](https://www.cmit.cn/html/tongzhigonggao/show-144-45826-1.html)

## 3. 已有方案中应先改的五个判断

### 3.1 “政策完整”不等于“声明抽取完整”——最重要

当前 `consistency.py` 对完整快照中没有候选 claim 的行为输出 `NOT_DECLARED`。该规则现有解释文字已提示人工复核，但接入自动抽取后不能仅靠 COMPLETE 推断没有声明。

本轮只读内存探针：删除合成输入的所有 `policy_claims`，原文和哈希不变，核验结果变为 `NOT_DECLARED`。说明漏抽条款可能变成缺失候选，而不是模型抽取失败。

**建议：分开记录 `snapshot_completeness`、`extraction_status` 和 `review_status`。** 没有抽完、模型失败、附件未取到、版本范围未定时，优先输出 `INSUFFICIENT_EVIDENCE`；成功抽取但尚未复核的缺失只展示“候选缺失，待复核”。允许人工核对全文/相关附件并完成定向检索后输出“本次快照未找到对应条款”，仍不是断言客观不存在。

正向匹配有一句原文可举证；负向缺失需要范围与检索过程，两者不是同样的证明问题。单靠 JSON schema 或原句子串校验不能证明模型没有漏抽。

### 3.2 原句存在，不等于意思抽对

`PolicyClaim.action` 只有 ACCESS/UNKNOWN，尚无否定和条件字段。

“我们不收集位置”“仅在用户选择附近功能时读取位置”“若拒绝授权，不读取位置”都可能包含同一关键词。合法 JSON + 原句确实存在，仍可被错误解读。

建议新增受约束的 `polarity`（肯定/否定/未知）、`condition`、`subject`、`claim_scope`；不在 20 天内尝试完整法律语义系统。MVP 至少把否定与复杂条件条款送人工复核，不能默认 ACCESS。否定声明与静态调用同时存在，也只能称“存在待复核的表达/条件差异”，不能证明 App 违背否定承诺。

### 3.3 缺失语义和证据类型的校验，不能让模型自行补

现引擎的 `has_api` 检查 behavior 引用中是否有 kind=API，并没有重新核实该 API 是否映射到此 data_type。

本轮将合成 API 摘录改为普通日志、locator 改为 unrelated/logging，Pydantic 仍接受并产生 EXACT_MATCH 等状态。**这是信任边界缺口，不是说明已有真实扫描器会如此输出：扫描器目前尚未实现。**

建议调用点必须带完整方法 descriptor、映射 rule_id 与规则版本，由可信归一化层核实 API→数据类型；不允许任意 JSON 通过贴 API 标签成为敏感行为。引擎接口仍保持纯函数，不直接依赖 Androguard/JADX。

### 3.4 当前全文快照实际有 10,000 字符瓶颈

`PolicyDocument.text` 允许 200,000 字符；但对应 `Evidence.excerpt` 最多 10,000，而且必须与全文相等。本轮构造 12,032 字符快照时，验证在 evidence excerpt 长度处失败。

建议全文存为可哈希 artifact，政策文档证据引用 artifact/hash，原句证据保留有限 excerpt 和 span；短期也可按 kind 分开限制。不要只截前 10,000 字符却继续声称快照 COMPLETE。当前还有最多 2,000 evidence 的输入上限，扫描器需明确截断/汇总规则并报告覆盖不足，不能静默漏掉调用点。

### 3.5 “代码精确行号”和“多来源冲突”都不能过度承诺

- 现开发计划把 JADX 行号作为每条代码证据的硬门槛，过严。JADX 官方明确反编译可能不完整。[JADX 官方 README](https://github.com/skylot/jadx)
- 主定位改为：`APK SHA-256 + DEX 文件 + caller 方法 descriptor + invoke offset + target descriptor`；JADX 显示行号只是固定工具/配置下的阅读视图，允许反编译失败时使用指令摘录。
- 当前跨政策来源规则未证明两个快照适用于同版本/同地区/同产品范围。它更适合叫“不同来源候选差异”，先比较适用范围与时间，不能用旧官网政策对照新 APK 后称矛盾。
- 现有 `EXACT_MATCH` 只表示数据类型匹配，保留此 scope；用途/接收方未知时不得显示“隐私政策全部一致”。

## 4. 与已有工作的关系与真正能讲的贡献

| 工作 | 一手资料已证明的重叠 | PrivacyTrace 应如何应对 |
|---|---|---|
| VioDroid-Finder | Android 权限/API/GUI 静态分析映射个人信息，并与政策核验 | 不宣称“APK+中文政策比对”首创；可作方法与样本参考 |
| PoliCheck | 数据流与披露比对，关注主体/接收实体 | 不把数据类型匹配冒充完整数据流/接收方核验 |
| PriBOM | 隐私信息清单、移动 App 静态分析、政策生成与可追踪协作 | Evidence Graph/traceability 不是单独首创点 |

来源：[VioDroid 官方项目](https://github.com/das-lab/VioDroid-Finder)、[PoliCheck USENIX 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/andow)、[PriBOM PoPETs 2025](https://petsymposium.org/popets/2025/popets-2025-0136.php)。细节与资料可用性另见 `2026-10-03-related-work.md`。

### 建议主贡献：把“负向结论”也做成可复核的证据闭环

不要只是为命中结果画图。把系统自己的工作落实为四项可检验产物：

1. **版本化规则与证据归一化**：明确权限/API/SDK的不同证明能力，数据类型映射可追到规则条目。
2. **政策覆盖与缺失核验门槛**：区分全文缺失、抽取失败、语义不确定、未复核和已复核候选；记录为什么系统选择不知道。
3. **人工复核事件链**：模型给候选，审阅者修订，保存旧值/新值/原因/证据，重新运行规则；不默默覆盖结果。
4. **验证后的解释交互**：用户能分辨“存在能力”“存在调用点”“测试中观察到”，且能定位到依据；用小规模对照验证，而非仅展示美观。

这些是本项目建议的自研实现与评价目标，**不是声称无人做过上述概念**。必须有代码、测试、标注数据和消融对比，才比“工具拼装”更有说服力。

建议消融：同一留出样本上比较“权限+关键词”“API+扁平匹配”“完整方案（层级、覆盖门槛、人工复核）”；报告误报、漏报、弃判与审阅成本。完整方案若没有实际改善，也要如实记录，不提前写显著提升。

## 5. 20 天提交版：做什么、不做什么

### 必做

- 本机 CLI/受限文件导入真实 APK，冻结哈希、包名、版本、来源。
- Manifest 能力 + 全部可解析 DEX 的有限敏感 API 调用点；4–6 个类别可人工核对。
- 至少一类有限 SDK 指纹样例；只显示“组件存在线索”，归属不明时 UNKNOWN。若工期不足可降为 P1。
- 政策人工上传/保存快照、分句、候选 claim 编辑、原句/span校验。
- 人工结构化输入先跑通；LLM 是可替换抽取插件，有关闭开关与缓存。
- 现有六状态规则 + 覆盖/范围门槛 + 明确静态措辞。
- 真实报告与证据下钻；记录未覆盖项、失败与复核过程。
- 受控 APK 端到端评测、少量真实样本复核、可离线回放的提交包。

### 这版不做

- 任意国产商业 APK 通用脱壳、混淆语义还原、native/Flutter 完整数据流。
- 全量 FlowDroid、自动模拟器遍历、Frida/抓包作为主链依赖。
- 独立开源 Repo 语义分析器、GitHub PR Bot、Delta 主线。
- Neo4j、向量库、RAG、多 Agent 产品架构、大型 Dashboard。
- 公网任意上传、登录系统、多租户、自动政策爬虫。
- 总风险分、合法/违法、安全/不安全、是否应卸载的裁决。

不是永远砍掉这些能力，而是避免 3 个编码位在 20 天里铺 8 条技术战线。**保底验收只要求1个真实样本、6～8个受控端到端场景、可复核报告与完整提交包；更多真实样本、12～16场景和用户试测均为冲刺项。** 不将成员持续全日投入视为已知事实。

## 6. 推荐技术栈与接口边界

| 层 | 推荐 | 团队负责 | 不应承诺 |
|---|---|---|---|
| 前端 | 保留 Vue 3/TS/Vite | 报告、局限提示、复核、证据下钻 | 为对齐历史讨论改成 React |
| API/规则 | 保留 Python/FastAPI/Pydantic | 契约、状态、纯函数规则、结果读取 | FastAPI 自动提供沙箱 |
| APK/DEX | Androguard，固定实测版本 | adapter、调用点、映射、失败记录 | 调用图等于真实数据流 |
| 阅读视图 | JADX 受限子进程 | 稳定 locator 关联、局部摘录、超时降级 | 原源码/原行号可完全恢复 |
| 政策 | 无损分句 + 规则基线 + 可选 LLM | 引用校验、否定/条件、覆盖记录、人工编辑 | 有原句就没有语义幻觉 |
| 存储 | 私有 artifact + JSON；复核记录可用 SQLite | 事务性保存、重放与删除 | 只写 schema 就算持久化完成 |
| SDK | 小型版本化指纹规则 | matched_feature、来源、误匹配复核 | SDK 存在即已采集/发送 |
| 增强 | 后续 FlowDroid/JVM worker | source/sink配置、资源限额、结果归一化 | 首版必须能跑全部大 App |

Androguard 官方 XREF 说明支持方法等交叉引用，同时要求加载 multidex，外部方法也不一定是 Android API。[Androguard XREF 文档](https://androguard.readthedocs.io/en/latest/intro/xrefs.html) 该文档含旧版示例，不能照抄为当前库 API；实际安装版本的 adapter 要做小样本 smoke test 并锁定。

**最小运行路径：**

```text
冻结 APK/政策
  ├─ 隔离解析进程 → Raw Evidence → Taxonomy/Rules → PrivacyBehavior
  └─ 快照/分句 → 规则或模型候选 → 人工核对 → PolicyClaim
                 ↓
       范围 + 覆盖 + 适用性校验
                 ↓
    纯规则 evaluate → Findings/Review Queue
                 ↓
      持久化/离线重放 → Vue 报告
```

不要让几十秒或数分钟的解析同步占住 evaluate 请求。第一版一个独立 worker、串行作业与可取消子进程就够；未证实吞吐需求前不引入 Redis/Celery。

### 建议的新字段（不是本次已实现接口）

- Artifact：hash、大小、包/版本、官方来源、采集时间、split清单、私有路径。
- Evidence locator：dex_entry、caller_descriptor、invoke_offset、target_descriptor、rule_id；可选 decompiled_file/line。
- Provenance：工具/版本/参数、APK hash、规则版本、原始输出 hash。
- Coverage：DEX 发现/完成数、provider状态、超时/截断、未覆盖范围及原因。
- Policy：raw hash、normalized text hash、明确的原文坐标系、applicable_version/region、附件清单、抽取状态。
- Claim：polarity、条件/主体、原句 offsets、抽取器/model/prompt版本。
- Review：reviewer、时间、修订前后、原因、所依据证据；单独保存，不塞进代码事实。

证据等级是离散的来源/证明能力，不是给任意 API 打 0.87 的“科学概率”。未校准的模型自评分不作为核验正确率。

## 7. 闭源国产 APK：分级支持而不是笼统“支持”

| 输入状况 | 首版交付 | 必须显示的局限 |
|---|---|---|
| 普通 Java/Kotlin/multidex | Manifest与invoke点，定位、有限组件匹配 | 不证明可达性、触发和外传 |
| R8/混淆 | 能解析的 descriptor/调用点与原符号 | 不承诺恢复业务命名/用途 |
| 疑似加固/仅加载壳 | Manifest及可见层线索 | 加固只能疑似；业务 DEX 可能未覆盖 |
| JNI/native/Flutter | 库/框架线索与有限 Java 层 | 不宣称理解 native/Dart 行为 |
| Hybrid/WebView | 可见桥接调用/静态资源线索 | 远端内容与小程序逻辑未覆盖 |
| Split APK/动态模块 | 冻结获取到的包集合；不完整集合降级 | 仅 base 不代表整个 App |

Android 官方说明 split APK 与动态 feature 可以承载额外代码/资源，因此包集合和采集环境必须成为分析范围的一部分。[Android App Bundle 格式](https://developer.android.com/guide/app-bundle/app-bundle-format) 不支持 split 输入时应明确拒绝或标为部分，不能假称完整分析。

样本优先选：官方来源明确、无需账号即可静态检查、政策可取得、可见 DEX、规模适中的国产 App。首个样本不是必须选微信/支付宝等复杂超级 App。具体品牌/版本待预筛，**目前没有实际判断某个 App 是否加固或采用某框架**。

静态采集不自动运行 APK。解析器也处理不可信输入，应置于专用低权限容器/虚拟机：限制 CPU/内存/时长/磁盘、默认断网、只读输入、独立临时目录、无宿主密钥挂载。只用普通子进程不等于安全隔离；没有隔离条件时先跑团队自建 fixture，不对任意输入开放服务。

若后续做动态，只针对明确授权样本和隔离测试账户；Frida/代理未观察到、pinning不可解密、场景没触发都保留未知，不推出“未采集”。[Frida Android 文档](https://frida.re/docs/android/)、[mitmproxy 证书文档](https://docs.mitmproxy.org/stable/concepts/certificates/)

## 11. 评测：分开“能解析”“判得准”“看得懂”

### A. Controlled APK：有真值的端到端测试

保底完成 **6～8个固定行为/政策场景**，冲刺目标 **12～16个**，而不是声称已完成原规划20～30个。最先保证权限无调用、敏感invoke、上位类别、否定、漏抽、部分政策和multidex/失败中的可构建场景；余下边界先由契约单测覆盖，再补APK端到端验证，两类数量分开报告。场景可装在少数测试 APK 中，但同一 APK 的多个变体不能伪算独立 App 数量。

覆盖：权限无调用、明确敏感invoke、SDK仅存在、上位类别、下位类别不覆盖上位、明确否定、条件声明、模糊表述、完整原文漏抽、政策部分/附件缺失、长政策、multidex、JADX失败、无效API映射、版本范围不同、解析失败。

正例真值由团队已知源代码/invoke和标注政策建立；负例用已知范围内的无对应invoke/条款建立。规则测试之外必须实际走过 APK adapter，否则仍不是端到端分析评测。训练/调规则与最终留出用例按 App/政策族分开，避免同模板泄漏。

### B. Real-world APK：现实证据复核，不编造完整真值

保底是 **1个官方渠道真实国产App**；时间允许才扩展为 **3个代表App + 1个挑战样本**。挑战可出现加固/native/范围不足，诚实的部分或失败报告也是结果。已有7个目标保留为后续扩展，而非20天硬指标。

至少两位编码成员独立核对一部分调用点/政策判定，再记录分歧与裁决。D可以负责原文定位，不独自作最终代码标注。

闭源样本完整真实行为不可得，不能把自家扫描输出同时当 Ground Truth。对人工可核对部分报告精度；全行为 recall 不可测时写不可测。报告每个样本的可解析DEX、条款审阅范围和未知，不用挑战失败样本从分母里消失。

### C. 指标与对照

- evidence：已知调用点的precision/recall，mapping准确率，稳定定位率。
- policy：条款级data_type/polarity/condition抽取指标；原句引用通过率与漏抽分别报告。
- finding：每状态混淆矩阵；特别统计错误缺失候选、partial误判与UNKNOWN/弃判率。
- workflow：解析成功/partial/失败数量、耗时与峰值内存、人工修订次数和时间。
- 同时报告自动候选表现和人工复核后表现，不能把人工修正后的分数包装成自动算法分数。
- 小样本先报真实计数与分母约定，再给precision/recall/F1；分母为零写N/A，不填100%。

### D. 用户理解（探索性，不是“大规模实验”）

时间允许招募6～10名非项目成员、不熟隐私技术的参与者，匿名同意后做短任务；这是便利抽样的形成性测试，不代表全体用户。

对照“权限+政策原文”和PrivacyTrace，任务是区分权限与发生、识别已声明类型、定位原句、发现系统不知道；交叉顺序/等价案例避免第二次熟悉效应。记录正确数、定位时间、误解次数。没做实验就不写“提升理解xx%”。

## 12. 三至五分钟演示与答辩口径

1. **30秒：问题。** 同一App有权限/API线索与长政策，普通用户不容易判断证据到底说明什么。
2. **60秒：真实输入。** 展示官方渠道、包名版本、APK hash、已冻结政策；上传分析或打开明确标注的历史报告。
3. **90秒：三个有依据的结果。** 一条具体类型声明、一条粒度/模糊项、一条证据不足或候选缺失；不强求现实样本出现违法/异常。
4. **60秒：核心自研。** 打开DEX定位和政策span；演示人工更正漏抽后重新核验，解释为何这比一个LLM总结可靠。
5. **30秒：局限与验证。** 挑战样本显示未覆盖；展示受控用例与小规模复核结果，说明工具/团队贡献。

风险回退：真实解析耗时无法在现场完成时，演示预先冻结同一输入的报告，标“历史分析回放”，同时保留 CLI 日志/产物hash；不使用假进度条冒充实时分析。

推荐名称口径：“PrivacyTrace：面向普通用户的 Android 隐私声明证据核验工具”。不用“测谎仪”“法官”“偷偷窃取”“100%自研”“完美反编译”“必获满分”。

## 13. 比赛提交与原创性材料

当前官方评分框架为：选题10、创新/原创25、技术25、完成度/可验证20、应用/传播10、展示/答辩10。其明确不以代码量或功能数量统一评价；使用成熟工具时仍核验团队的再设计和新增贡献。[官方评分标准，附件2](https://static.cmit.cn/uploadfile/2026/0924/%E9%99%84%E4%BB%B62%202026%E5%B9%B4%E7%AC%AC%E5%8D%81%E5%B1%8A%E5%85%A8%E5%9B%BD%E5%A4%A7%E5%AD%A6%E7%94%9F%E6%95%B0%E5%AD%97%E5%AA%92%E4%BD%93%E7%A7%91%E6%8A%80%E4%BD%9C%E5%93%81%E5%8F%8A%E5%88%9B%E6%84%8F%E7%AB%9E%E8%B5%9B%E8%AF%84%E5%88%86%E6%A0%87%E5%87%86%E5%8F%8A%E5%A5%96%E9%A1%B9%E8%AE%BE%E7%BD%AE.pdf)

应准备：可运行作品/操作说明、演示视频、测试/失败记录、成员实际工作表、第三方工具与数据/素材来源清单、生成式AI使用说明。官方通知要求披露工具、环节、流程/prompt、人工筛选修改和团队贡献；它不是“用了AI一定加分”或“套壳直接零分”。[官方通知](https://www.cmit.cn/html/tongzhigonggao/show-144-45826-1.html)

项目根目录当前没有源码 LICENSE；使用公开代码、数据集、SDK signature前分别核对许可，公开可下载不自动意味着允许重新分发。APK、完整反编译输出、凭据、未脱敏运行数据留私有路径；公开政策/摘录也按实际授权审查，不能默认全文可再发布。提交前记录第三方依赖版本与NOTICE/许可，不使用笼统“100%自研”。

**待确认：**附件1参赛指南本轮读取失败；精确赛项、材料格式/大小、报名资格与学校内部流程未核验。这里不锁死赛道，也不据历史聊天猜格式，需指导老师确认。

## 14. 赛后/更充足工期的扩展顺序

1. 扩大真实样本到现规划7个，规则/API覆盖与语义复核更扎实。
2. 在自建授权样本做场景化动态观测，与静态潜在调用对照；保留未触发/不可解密边界。
3. 只对可处理小样本接FlowDroid；用已知source/sink真值评价，超时不阻断基础报告。
4. 再考虑版本变化归因、PR集成或完整Repo通道；先解决稳定证据身份和政策适用版本。

若最终只有一个人能稳定编码，就进一步降为CLI证据采集 + 人工政策结构化 + 现有报告，不做LLM实时接入。若有两个月以上，不只是多堆功能，应优先提高基准质量、误判控制与可复现性。
