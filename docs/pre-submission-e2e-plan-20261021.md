## 3. 唯一业务主线与成功判据

实际客户端选择已安装 App → 用户确认单 APK 或完整已安装 splits 集合 → HTTPS 能力协商与上传 → 同一任务的政策发现/辅助补入 → 持久任务与队列 → Runner 的实际隔离扫描 → Android 报告 → 静态证据与政策原句下钻。

每个成功案例同时满足：

1. 客户端确认的包名、版本、组件清单、各文件 SHA256 与服务端回读一致；包集合没有被悄悄降为 base-only。
2. 使用正确的实例和任务访问材料；记录实际队列、执行尝试与隔离扫描的关联，不能只看上传成功或 SUCCEEDED。
3. 报告来自本次输入与扫描，至少实际核对一处静态证据所属包/代码位置及一处政策原句区间；受控材料的预期在运行前固定。
4. 保留 UNKNOWN、PARTIAL、UNREVIEWED 及附件未知状态；权限和静态调用线索不表述为运行时实际采集、安全或违法结论。
5. Android 能显示、恢复并下钻该任务；Web 对同一报告保留证据与状态。旧任务或旧实例的迟到响应不能覆盖当前对象。
6. 证据包括客户端动作、脱敏接口观察、持久状态、真实容器隔离及报告引用链。单张截图、bridge 替身和预制报告不能满足此判据。

术语沿用 [被跟踪的项目词汇表](https://github.com/MrEcho114/PrivacyTrace/blob/68015de0e1e0881225c3c12fedbe6df958a60898/GLOSSARY.md)。本方案不修改当前工作区来源未确认的同名文件；时间安排和测试顺序可调整，无需另造架构 ADR。

## 4. 完整矩阵与执行顺序

### 4.1 成功组合：12/12

“标准配置”和“自托管配置”均部署在本机，保持独立实例身份、访问材料与数据；前者对应旧表中的“官方”配置，不代表已访问公网官方服务。

| 输入 / 本机配置 | 自动政策 | 网页辅助补入 | 手机模型 API 补入 |
| --- | --- | --- | --- |
| 单 APK / 标准配置 | H01 | H02 | H03 |
| 完整 splits / 标准配置 | H04 | H05 | H06 |
| 单 APK / 自托管配置 | H07 | H08 | H09 |
| 完整 splits / 自托管配置 | H10 | H11 | H12 |

先复现并封闭 BUG-01，再跑 H01/H04，确认单包和 splits 均经过正确检查器；随后完成其余十项。辅助路径必须从同一任务的政策缺失/不完整状态进入，不绕过真实上传、扫描与引用校验。网页和模型输入使用本机受控内容，不据此声称外部聊天或模型查找质量已验证。

H03/H06/H09/H12 使用专用本机 HTTPS 模型 API 接收器及一次性测试凭据，由同一实际 Android 客户端走模型适配、TLS、Key 投递与候选回写，再接回原任务。受控的是模型服务响应，客户端传输和业务接线必须真实执行；不能用 bridge 替身或组件 Mock 代替。环境缺失则记 BLOCKED，不缩减分母。

## 7. 缺陷处理与复测规则

- 阻断主线、报告/引用错误、任务或模型凭据泄露、跨任务/实例访问、删除后复活和崩溃，均阻止通过；失败须保留首个可复现证据。
- 对应子票执行人先建立确定的失败入口，再由当前模块 owner 修复，并证明该入口由失败变为通过；新增回归应锁住实际接缝。通过组件测试后仍须重跑原本机案例，共享源码不得由多票同时覆盖。
- 环境反复重启按独立问题处理：记录中断点与任务状态，修复专用环境持续性，再重跑受影响案例；不关闭宿主的其他发行版或整体 daemon。
