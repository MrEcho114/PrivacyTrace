## 三、代表性人机协同工作流（2 个）

### 场景 1：Android 敏感权限与调用点的静态规则脚手架

- **AI 介入目的**：协助梳理 Android 敏感权限与 API 签名的常见调用形态，产出正则匹配与 AST 遍历的候选骨架。
- **代表性输入（摘要）**：请列举 Dex 反编译后与 `ACCESS_FINE_LOCATION`、`READ_MEDIA_IMAGES` 相关的常见反射与动态代理调用形态，并给出可测试的匹配模式候选。
- **AI 输出**：通用反射片段与初步正则表达式候选。
- **团队的筛选、修订与人工核心贡献**：候选模式在受控沙箱中假阳性偏高，团队剔除了其中的动态执行代码，改为**确定性静态字节码归因引擎**，调用点定位保留类／方法／字节码偏移，并补上反射、动态加载、Native 与混合同的边界声明。规则未命中一律保留为 `UNKNOWN`，不外推为“未采集”。

### 场景 2：展示材料文案与作品展示视频分镜

- **AI 介入目的**：辅助整理对外展示页的文案候选与作品展示视频的分镜／旁白结构。
- **代表性输入（摘要）**：给定已定稿的功能清单、界面截图与时长约束，要求产出可直接替换的文案候选，以及逐镜可拍摄的分镜表。
- **AI 输出**：文案候选与分镜骨架（镜头序号、画面内容、字幕建议）。
- **团队的筛选、修订与人工核心贡献**：文案由团队逐条改写后落盘为仓库内文案文件，来源记录在同目录的 provenance JSON（`copy.ts` 与 S0／S1 记录）；分镜按可拍摄性逐镜删改，最终成片为真实界面录屏叠加动效，**未使用 AI 生成图像**。视频中的所有指标与数字由实际命令输出填入，不由模型补造。

## 四、团队原创贡献与验证边界

1. **核心逻辑自主**：核心架构设计、静态证据匹配引擎、判定规则、受控隔离环境与验证评估由团队成员实现；AI 辅助集中在脚手架、测试与文档／文案层面。本文不给出 AI 代码比例。
2. **验证方式**：交付数字来自实际命令输出，可由仓库门禁 `bash scripts/check.sh`（Windows 入口 `scripts/check.ps1`）与受控部署验收入口复跑。
3. **可复核范围**：限于本包 `05_补充成果材料/` 内的 `验收摘要.md`、`deployment-summary.json`、`spec30-browser-proof.json` 与截图目录。**本包不提供完整的内部验收收据**。
4. **产品运行时的可选外部模型**：政策候选句抽取能力默认关闭，需使用者自备 API Key 并显式开启；默认模型为 `gpt-4o-mini`、默认服务地址为 OpenAI 兼容端点，实测流程使用 `deepseek-flash`。该能力属产品功能而非研发工具；模型权重、API Key 与调用日志均不随包分发。
5. **不替代人工判断**：AI 不直接判定隐私结论。报告中的权限、线索、政策声明与状态由规则与用户材料产生，未复核状态保持 `UNREVIEWED`／`PARTIAL`／`UNKNOWN`。
6. **不做过度声明**：不声称“完全无 AI 参与”，不给出未经逐文件复算的 AI 代码占比，也不作任何排他性自主性表述。
7. **数据边界**：未向未经批准的外部服务发送 APK、政策全文、反编译代码、个人信息或凭据。
