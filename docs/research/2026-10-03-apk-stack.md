# PrivacyTrace APK 证据采集技术栈调研（2026-10-03）

## 范围与结论

本备忘录针对闭源国产 APK 的隐私声明辅助核验，复核仓库 README 与 `docs/development-plan.md` 的初始路线。目标是提取可复核证据，不判断违法、是否真实收集、是否恶意，也不把“接口存在”说成运行时发生。未下载、安装或执行任何未知 APK。

**建议结论（工程建议，非已验证项目实现）：**先做 APK 文件指纹/包元数据、二进制 Manifest 权限、DEX 中敏感 API 调用点及字符串/SDK 线索；证据定位以 DEX 方法/调用点/指令偏移和工具版本为准，JADX 源码行只做辅助展示。以 Androguard 做解析与结构化提取、JADX CLI 做人工可读反编译；FlowDroid 列为后续可选实验，不纳入首周主链。动态采集仅在授权、隔离的模拟器或专用设备中观察用户触发的有限行为；Frida 与 mitmproxy 均不得作为绕过登录、反检测或证书锁定的手段。TLS pinning 时记为“网络内容不可见/样本限制”，不移除 pinning。

## 已核验：工具能力与边界

| 工具 | 官方资料核验到的能力 | 对本项目的边界/用法 |
|---|---|---|
| Androguard | 官方文档列明 APK、DEX、Android 二进制 XML/资源解析，DEX 反汇编；Python API `AnalyzeAPK` 返回 APK、DEX 列表和 Analysis。Analysis 支持类/方法/字段/字符串交叉引用。 [文档](https://androguard.readthedocs.io/en/stable/index.html) · [AnalyzeAPK API](https://androguard.readthedocs.io/en/stable/api/androguard.html) · [Analysis API](https://androguard.github.io/androguard/reference/androguard/core/analysis/analysis.html) | 适合 Python 后端提取 Manifest、DEX 元数据、方法/字符串证据。XREF/调用图是静态结构，不证明代码可达或运行，更不证明数据外传。DEX 解析不能解开任意加固/运行时解密内容。建议先确认当前库版本、输入坏包与 multidex 的异常处理。 |
| JADX | 官方 CLI 接受 APK/DEX/AAB 等输入；可输出资源与 Java 样式源码，支持 `--add-debug-lines`（仅在调试信息可用时）、`--show-bad-code`、fallback 指令输出、混淆映射等选项。[官方 README/CLI](https://github.com/skylot/jadx/blob/master/README.md) | Java 是对字节码的重建视图，不等于原始源码；控制流、变量名、注解及行号可能缺失或不可靠。官方工具提供“不一致代码”及指令 fallback，意味着不能把反编译源码当作无误事实。主证据宜记录 DEX method descriptor + invoke 指令/偏移；JADX 文件/行号作便于用户理解的辅证。映射文件通常只有开发者提供时才有用。 |
| FlowDroid | 官方项目称其静态计算 Android/Java 数据流；流程需要配置 Android SDK platforms、APK、taint wrapper 与 source/sink 定义；默认 StubDroid summaries 可用于数据流分析。[官方仓库](https://github.com/secure-software-engineering/FlowDroid) | 不是自动理解“隐私目的/接收方”的工具。source/sink 定义和库摘要决定覆盖范围；漏建模、反射、动态加载、native/JNI、SDK 缺失会造成漏报或误报。官方说明大型应用运行可能耗时，并且性能/精度/召回需权衡（同仓库 README）。建议首周不以它作为交付阻塞条件。 |
| Frida | 官方定义为动态插桩工具，可在进程中注入脚本、枚举模块/导出符号、跟踪函数；Android 入门以 rooted 设备上的 frida-server 为主，也列出 Gadget/调试器等替代方式，并提示 ROM 差异可能导致问题。[官方概述](https://frida.re/docs/home/) · [Android setup](https://frida.re/docs/android/) · [模式](https://frida.re/docs/modes/) | 观察的是特定设备、版本、账户状态、输入、时间窗口下触发的执行；未触发不等于不存在。root、注入与重打包改变测试条件，应用可能拒绝运行。项目只用在自有/明确获授权样本和专用隔离测试环境，预先列出观测点，不共享可复用绕过脚本。 |
| mitmproxy | HTTPS 中间人代理通过其 CA 动态签发站点证书；官方明言 pinning 会拒绝代理证书，若要拦截此类连接就要修改应用，并建议不重要的主机使用 ignore_hosts。[证书说明](https://docs.mitmproxy.org/stable/concepts/certificates/) | Android 7+ 应用默认可能不信任用户 CA；应用也可能自带信任库。代理只看到经过代理且可解密的流量，不覆盖直连、QUIC/自定义协议或无法解密连接。即使看到域名/字段，也通常不能单独证明接收方的法律/组织身份或处理目的。采用“失败/不可见”作为有效结果，停止在 pinning，不改包绕过。Android 官方也提供应用级 pinning 与 debug-only 配置说明：[Network Security Config](https://developer.android.com/privacy-and-security/security-config)。 |

## 已核验：重点覆盖缺口

- **混淆/压缩：**JADX 有启发式重命名及加载映射文件能力，但语义命名不能从短符号可靠恢复；R8 官方说明 mapping file 位于构建输出，可供开发者映射回原名。闭源 APK 通常没有 mapping 文件，不能承诺还原。[JADX README](https://github.com/skylot/jadx/blob/master/README.md) · [Android R8 troubleshooting](https://developer.android.com/topic/performance/app-optimization/troubleshoot-the-optimization)
- **加固/动态载荷：**本次官方资料核验支持的工具覆盖是 APK 中可解析的 DEX/资源；未找到可保证对国产加固壳通用脱壳的官方能力声明。因此将壳特征、DEX 缺失/不完整、运行时加载等标注为覆盖限制，不承诺恢复。
- **Native：**Android APK 可包含 `lib/<abi>/lib*.so` 原生库；Androguard/JADX 的 Java/DEX 路线不能等同于 native 代码数据流分析。首版只盘点库名、ABI、导出符号/字符串（若可获得），native 行为归为未覆盖或人工复核。[Android NDK ABI 文档](https://developer.android.com/ndk/guides/abis)
- **Flutter：**生产 Flutter 将 Dart AOT 编译为本机代码，Flutter 引擎与应用代码都可能以 native library 形式出现；仅扫描 DEX 不足以解释 Dart 应用逻辑。[Flutter 官方 FAQ](https://docs.flutter.dev/resources/faq)。首版识别并声明覆盖差异，不声称恢复 Dart 源码。
- **Hybrid/WebView：**Manifest/DEX 能提供 WebView、JS bridge、URL/域名等静态线索，但实际 Web 内容可远端变化。Android 文档指出传统 `addJavascriptInterface` 暴露给所有 frame；应把 bridge 调用视为能力线索，而非已发生数据访问。[Android JS bridge 文档](https://developer.android.com/develop/ui/views/layout/webapps/native-api-access-jsbridge) 动态 WebView 内容还受测试时服务器返回内容影响。
- **TLS pinning/流量：**pinning 是阻止中间人代理的一种应用设置；mitmproxy 官方要求修改应用才能拦截，PrivacyTrace 不应以其“可绕过”教程为产品依赖。即使流量可见，目的和数据接收方仍需独立证据，不能由 API 名、URL 字符串或域名直接定性。
- **Purpose / Recipient 推断：**敏感 API、调用路径、字符串、网络主机只能支持“潜在能力/线索”。代码无法普遍证明调用场景中的用户意图、业务目的、实际后端控制者、共享关系、保留期限或运行时发送成功。沿用仓库三分法：代码事实 purpose=`UNKNOWN`；目的与接收方若政策有原句则是政策声明；其余单列低置信度推断并给证据，不参与硬性法律结论。

## 对既有方案的收敛建议

1. README 对 Androguard/JADX 的“成熟”定位可保留，但 `development-plan.md` 中“完美解决”一类表达应改成“提供可复核底层解析/反编译能力，输出仍需验证”。官方资料本身提供不一致代码/fallback 选项，不能宣称完美恢复。
2. 第一阶段目标限定为 1 个授权、公开发行渠道样本：冻结 APK SHA-256、包名/版本、来源 URL 与获取时间；提取 Manifest 权限、DEX 敏感 API invoke-site、必要字符串/SDK 线索，联结一份对应版本政策的原句。没有真实样本可先用自建开源测试 APK/人工样本，但标明非真实评测。
3. Evidence schema 给每条证据记：源 APK 哈希、工具/版本/配置、DEX 文件与方法签名、偏移或指令片段（稳定定位）、可选 JADX 文件/行号、解析状态/覆盖说明、人工复核状态。政策快照单独哈希。错误/未知也要显式保存，禁止静默跳过。
4. 不首周接入自动动态分析；若要展示动态能力，用团队自建且明确授权的测试 APK，干净模拟器、无个人账户/真实凭据、快照回滚、只访问自建测试端点。Frida 记录预先定义的 API 调用；mitmproxy仅在该测试样本正常接受测试 CA 时记录。拒绝登录绕过、证书 pinning 绕过、反检测规避及第三方用户数据采集。

## 7 天验证关卡（建议）

| 日程 | 实施/验证 | 通过门槛与停止条件 |
|---|---|---|
| D1 | 固定样本策略与沙箱；仅选团队自建或公开且授权明确 APK；记录 SHA-256、包名、版本、来源；不得运行未知 APK。 | 样本来源、授权范围、隔离方案、清理方式均可追溯；否则只用自建 APK。 |
| D2 | Androguard 提取包元数据、Manifest 权限、所有 DEX、基础字符串；建立 JSON 输出与解析失败状态。 | 两个自建 fixture（普通、multidex）与手工核对一致；损坏输入失败可解释；hash 与输入吻合。 |
| D3 | 以 JADX CLI 导出源码/资源；与 DEX 指令位置对照 10 个已知调用点。 | 不要求源码行号稳定；每条样本证据可回到 method descriptor + invoke 指令/偏移；错位必须显示“行号非保证”。 |
| D4 | 实现敏感 API 分类白名单和调用点去重；标记 SDK/宿主包归属为启发式。 | 预置小型正负例集覆盖权限/API；人工核验每个阳性；不将权限单独升格为行为发生。 |
| D5 | 处理四种可见差异 fixture：R8/短名混淆、含 `.so` native、Flutter 标识、WebView bridge。 | 能识别并输出 coverage flags；无法理解的逻辑显示“未覆盖/未知”，不能出无依据完整结论。 |
| D6 | 证据模型与政策原句关联；做目的/接收方措辞审查；（可选）仅自建 APK 做隔离动态演示。 | 每个结论都能双向下钻至 APK 哈希/DEX 位置与政策原句；静态与动态证据类型不混淆；pinning 或不可解密流量记限制。 |
| D7 | 冻结 1 个样本，执行端到端回归与团队盲审，记录 false-positive、false-negative、覆盖缺口。 | 3–5 个结论全部有证据与人工复核；不声称法律判断/实际收集；任一证据无法复现则降级为“线索”或删除。 |

**最小可交付：**APK 哈希与来源记录 + Androguard Manifest/DEX JSON + JADX 辅助查看 + 敏感调用点规则集 + 证据卡片/盲审记录 + coverage flags。FlowDroid、Frida、mitmproxy 是后续研究或演示项，不是闭源 APK 普适核验能力承诺。
