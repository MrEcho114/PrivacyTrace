## 二、 角色分工与研发边界界定

### 1. 人工智能工具的使用边界（AI 负责：具体代码实现辅助）

在 PrivacyTrace 项目研发过程中，人工智能工具严格定位为**受控的代码实现与模板辅助工具**。AI 工具不参与系统架构决策、算法核心逻辑推演或业务规则裁决，其生成内容仅限于在学生团队预先制定的严格接口契约与沙箱约束下的具体代码实现：

1. **后端 API 胶水层实现**：根据学生团队定义的 API 规格说明书与 Pydantic 数据模型，辅助编写 FastAPI 路由转发、请求参数解析、HTTP 状态码映射及基础输入边界校验逻辑。
2. **数据契约与类型转换脚本**：编写契约导出工具脚本 [`scripts/export-schema.py`](../scripts/export-schema.py)，负责将 Python Pydantic 数据模型自动转换为符合 JSON Schema 规范的结构，并导出前端 TypeScript 接口契约（[`apps/web/src/contracts.generated.ts`](../apps/web/src/contracts.generated.ts)）。
3. **测试用例骨架与断言模板**：根据学生团队制定的测试规格与边界用例清单，辅助生成常规单元测试用例的代码骨架（如 HTTP 请求模拟、边界参数回退断言、类型防护断言等）。
4. **全流程受控执行机制**：AI 生成的任何代码片段均必须通过本地静态代码分析工具（Ruff、ESLint）、严格的 TypeScript 类型检查（`vue-tsc --noEmit`）以及前后端自动化测试套件（pytest、Vitest）的强制验证。未通过测试或存在异味的代码一律舍弃。

### 2. 学生团队的核心贡献（学生负责：核心架构设计、设计规范、代码审查、项目管理）

PrivacyTrace 项目的理论构思、核心架构、工程标准及安全性保障 100% 由学生团队独立研发并把控，具体体现在以下四个核心维度：

#### （1） 核心架构设计（Core Architecture Design）
- **Evidence 证据链追溯模型（参考 PRD [`docs/source/brief-extracted.txt`](source/brief-extracted.txt) Part 3 第 7 节）**：团队独立设计了 `PrivacyBehavior` 最小核验单元，定义了由 `DataType`、`Action`、`Purpose`、`Recipient`、`Transfer`、`TemporalScope` 与 `Evidence[]` 共同构成的完整追溯数据流，实现了“每一个结论均有可追溯的证据支撑”。
- **Consistency Engine 六态判定机制（参考 PRD Part 3 第 8/11 节与 Part 4 Epic 7 PT-701~708）**：独立构建了多源隐私政策一致性判定状态机，严格划分为 `EXACT_MATCH`（具体类型已声明）、`CATEGORY_MATCH`（声明粒度不足）、`NOT_DECLARED`（未找到对应声明）、`POLICY_SOURCE_CONFLICT`（不同来源声明有差异）、`AMBIGUOUS_DISCLOSURE`（相关声明不够清楚）与 `INSUFFICIENT_EVIDENCE`（证据不足）六种判定状态，并与 7 类核心隐私问题进行可解释映射。
- **Privacy Taxonomy 分类体系（参考 PRD Part 3 第 8 节）**：面向 Android 系统生态建立了 8 个一级敏感数据分类，并建立了 Android 运行时权限（Permission）、字节码 API 调用（API Call）与政策文本短语（Policy Phrase）之间的三向权威映射模型。

#### （2） 系统设计规范与红线约束（Design Specifications & Constraints）
- **事实 / 声明 / 推断三权分立**：在数据模型与存储层确立“推断出的 Purpose 永远不能作为已确认事实”的技术红线，防止算法与外部工具产生主观臆断。
- **措辞红线与中立性约束**：严格禁止在任何报告界面输出“违法/合法”、“安全/不安全”等绝对化法律与定性结论，严格规范为客观中立的技术事实陈述（如“存在潜在能力”、“未找到对应声明”）。
- **Docker 容器隔离沙箱方案**：针对未知 APK 设计并实现了 Docker 隔离执行环境（无网络访问、非 root 降权运行、只读文件系统挂载、显式内存与 CPU 上限约束、退出即销毁），杜绝分析过程中对宿主系统的潜在威胁。
- **运行时安全与防暴露策略**：后端服务强制仅绑定 `127.0.0.1` 本机回环地址，不设外部身份认证，严禁公网暴露，确保评测环境与用户隐私数据安全。

#### （3） 全量代码审查与缺陷排查（Code Review）
- **全量 PR 逐行人工把关**：仓库所有分支合并均经过严格的 Pull Request 人工审查（包括 PR #26、#27、#29、#33、#34 等），由团队核心成员逐行研判。
- **拦截高风险并发与逻辑漏洞**：在审查过程中，学生团队主动定位并排除了多处 AI 难以察觉的隐蔽工程缺陷，包括：
  - `job_store.JobStore._transaction` 并发文件锁竞争与死锁隐患；
  - Web 前端防 XSS 渲染逃逸边界（严格剔除 `v-html` 与 `innerHTML`，配置严苛 CSP 策略）；
  - 多源政策快照在并发摄取时的版本漂移问题；
  - 第三方 SDK 归属分析中的有界内存收集与截断回归问题。

#### （4） 项目管理与工程治理（Project Management）
- **全流程任务拆解与里程碑推进（参考 PRD Part 4 第 16 节）**：团队独立梳理并制定了覆盖 13 个 Epic（PT-001 ~ PT-1206）的完整开发路线图，主导推进了 S0 原型验证与 S1 隔离分析闭环两个关键里程碑交付。
- **CI/CD 自动化流水线建设**：自主搭建并维护 GitHub Actions 自动化持续集成体系（包括 API 单元测试、前端类型检查、Docker 容器构建与安全扫描测试）。
