## 第 5 页

全文共出现下列固定术语，含义以本表为准，避免组内表述漂移。
Evidence / 证 据
支撑某条结论的原始来源片段，必须可追溯到文件、
类、方法或政策原句。所有结论都要绑定 Evidence
IDs。
PrivacyBehavior
最小核验单元。由 DataType、Action、Purpose、
Recipient、Transfer、TemporalScope 与 Evidence[]
共同描述。
Taxonomy
隐私数据分类体系。MVP 控制在约 8 个一级类，支持
上位 / 下位类，并提供 Permission / API / Policy
Phrase 三向映射。
Static Evidence
静态分析结果，统一称为「潜在行为 / 静态证据」。不
等于「App 实际收集了数据」。
Observed Evidence
动态分析结果，统一称为「运行时已观察行为」。由 P1
动态模块把静态潜在行为升级而来。
EXACT_MATCH
政策表述与程序行为在数据类型层面完全对应，属于声
明充分的情况。
CATEGORY_MATCH
政策只写到上位类别（如只写「设备信息」），程序出
现具体类型（如 OAID）。既非完全匹配，也非完全未
声明。
NOT_DECLARED
该数据类型的访问行为在对应政策源中找不到任何相关
表述。
POLICY_SOURCE_CONFLICT
同一 App 的多个政策源之间结论不一致（如 App 内未
声明、商店却有声明）。
AMBIGUOUS_DISCLOSURE
政策有相关表述但过于笼统，无法据此确认具体数据类
型、目的或接收方。
INSUFFICIENT_EVIDENCE
当前证据不足以支撑任何结论。必须如实输出，不可用
推测填补。
多 源  Policy
IN_APP_POLICY / STORE_POLICY /
OFFICIAL_WEB_POLICY / SDK_POLICY 四个来源，分
别核验、不合并为一份。
Ground Truth
Controlled Benchmark 中人工确认的正确答案，用于
自动评测 Precision / Recall / F1。
AnalysisJob
一次完整分析任务的运行实例，承载输入 APK、规则集
版本、各阶段产物与状态流转。
措辞红线（全体必须遵守）
以下表述不得出现在任何界面、报告、答辩材料中：
✕  把「存在权限 / API」直接写成「App 实际收集了数据」； ✕  输出「违法 / 合法」总裁决； ✕  输出「安
全 / 不安全」总裁决； ✕  输出「建议卸载」类行动建议； ✕  把模型推断出的 Purpose 当作已确认事实陈
述。
正确替换：静态结果说「检测到代码中存在……的能力」；政策问题说「这份政策只写了……，没有明确说
明……」。

## 第 6 页

Part 1 · 项目定位与创新叙事
我们做什么，为谁做，凭什么算创新
01
项目定位
PrivacyTrace 是面向普通 Android 用户的 App 隐私体检工具。
它通过分析 APK 中的隐私行为证据，并与 App 的隐私政策、应用商店声明等信息进行一致性核验，将
专业隐私证据转化为普通用户能够理解、能够下钻复核的隐私报告。
核心表达
01 Android 权限告诉用户：App 被允许做什么
02 隐私政策 / 商店声明告诉用户：App 声称自己做什么
03 PrivacyTrace 尝试告诉用户：程序中存在什么隐私行为证据，以及这些行为是否被清楚声明
证据措辞原则
应该这样写
静态分析结果 → 潜 在 行 为  / 静 态 证 据
动态分析结果 → 运 行 时 已 观 察 行 为
不能这样写
把「存在权限 / API」表述成「App 实际收集
了数据」
直接输出「违法 / 合法」「安全 / 不安全」
「建议卸载」等总裁决

本稿的三个「不可动摇」
1. 措辞红线 —— 不把静态证据说成实际收集，不下合法/违法、安全/不安全、建议卸载的裁决。
2. 事实 / 声明 / 推断分开存 —— 推断出的 Purpose 永远不能当已确认事实用。
3. 所有结论绑定 Evidence IDs —— 不能只生成一段 LLM 自然语言就交付。
