## 可测试入口

1. 启动本机 API 与 Web，展开“政策来源”末尾的“找不到政策？使用网页辅助收集”。
2. 填应用名称或包名，复制指令。正文直接复用 #79 的 `COPY.txt`，仅追加用户输入的应用线索；
   复制不可用时可从只读文本框选择完整指令。网页聊天工具由用户自行操作。
   前端生成资源与 #79 原文保持一致，便于只复制 Web 目录的容器构建；更新原文后运行
   `node scripts/sync-policy-instructions.cjs`，使用 `--check` 或 Web 单测检测漂移。
3. 回填 collector/1 JSON 或兼容的旧单来源 JSON，检查后逐份确认来源类型，再补入当前材料。
   未知类型不默认官网；无正文、离线、未找到仍按原状态记录，不自动联网或补正文。
4. 选择 APK 后继续。已导入来源、原句、未勾选候选和服务端审计保留在同一草稿。
   只有 APK、没有政策线索时，调用既有发现接口，再按既有抓取/提取链路准备材料。
5. 准备中可取消。取消不能撤销已提交的服务端修改；点击“重新读取材料”确认服务实际状态。
   迟到响应不替换当前界面；恢复的新来源继续准备，已经处理的来源不重新生成用户删除的候选。

含外部收集审计的草稿不能在编辑来源后无声重建。可以重新读取原材料，或显式“新建材料版本”
并手动修正；新版本按手动输入，旧版本保留原收集审计和候选。模型摘要不进入政策正文。

## 本轮 P3 复核修复（后续提交）

- 自动候选提取抛错或服务端返回 `model_audit.status=FAILED` 时，不将来源加入已成功准备集合；返回材料页仍允许重新准备。候选页保留来源级失败提示及既有“重新提取候选”按钮。成功后才清除失败状态；已经存在候选或已成功准备的其他来源不会被无故重新提取。
- 恢复草稿时仅对服务端明确记载为 `FAILED` 的来源开放自动重试；未知提取历史不自动重建候选，以保留用户删除决定。取消后的迟到响应不能把来源标为失败或覆盖材料。

## P3 审计同步修复（最新提交）

- 服务端 `WebIntake._extract()` 在提交新的来源候选提取审计时增加草稿 `revision`，但上传、抓取及其他编辑同样可能增加全局版本；当前 `model_audit` 没有独立的提取操作 ID / 完成时间。因此单纯的版本增长或审计字段变化都不构成一次新提取成功的证明。
- `refreshMaterials()` 仅在读到更新的草稿版本，且来源审计 `status` 确实转为 `SUCCESS` 或 `PARTIAL` 时，清除本地失败状态；服务端明确 `FAILED` 仍优先标记失败。旧 `SUCCESS` / `PARTIAL` 的耗时、Token 数或其他元数据即使发生变化，也不清除较新的 HTTP 失败。
- 如果服务端重新提取得到与旧审计相同的成功状态，在缺少单次操作标识的条件下，刷新无法确定哪次执行更新了结果，前端保守保留重试入口；用户可显式重新提取，成功响应会清理失败标记。取消/晚到响应仍受现有请求信号控制。
- 在 `policy-assist.test.cjs` 中增加两个既有成功状态的元数据漂移回归、无版本推进的状态改变以及 `FAILED → SUCCESS` 新版本恢复回归；继续运行原有取消/恢复、多来源、候选保留测试。
- 本节为行为及回归范围记录；最终测试和 CI 结果应绑定本次最终提交 SHA，不能将历史 Windows 验证或上一轮 HEAD 的绿灯重新记作本次通过。

## 独立后续 PR：同状态提取成功的 attempt_id 对账

- 最初基于 PR #110 的 `9ae89e2` 单独叠加提交，PR #110 已独立合并，当前修复作为 PR #118 的增量提交。服务端候选提取接口继续兼容仅传 `revision` 的旧客户端；新客户端提供非鉴权用途的单次 `attempt_id`，服务端在提交候选与来源审计的同一事务内保存 `model_audit.attempt_id`。
- 前端只在当前组件内存记录每个来源最近一次请求标识与发起时草稿版本。取消、超时或响应丢失可能发生在服务端提交之后；显式重新读取时，匹配的操作标识和版本前进可恢复 `SUCCESS → SUCCESS` 或 `PARTIAL → PARTIAL` 的新执行结果。标识不匹配不覆盖本地失败；旧服务端不带标识时，仅保留先前状态变化与版本推进的兼容规则。
- 标识不存浏览器 localStorage，不包含政策正文或模型凭证，不代表人工审核结果。它是**相关性标识**而非服务端去重/幂等键；本次不添加任何自动模型重试。旧客户端请求不受新字段要求限制。
- 新增 API 同状态提取、旧客户端兼容、非法请求、失败审计与敏感信息不泄漏，以及前端响应丢失、取消恢复和标识错配的回归。最终测试、构建与 CI 应以本后续 PR 最新 SHA 为证据。

## P2 修复：连续重试对账与有界保留（PR #118）

- 复现路径：A 的服务端提取已提交，但 HTTP 响应丢失；用户未先刷新便再次请求 B，B 因旧 revision 返回 409；刷新仍须凭保存的 A 标识确认同状态的 SUCCESS / PARTIAL，并保留已检查候选，不能再触发第三次付费模型提取。
- 每个来源在组件内存中保留**最多 16 个**尚未对账的请求标识，而非单个最新标识。直接确认提取结果，或刷新匹配任意未确认请求的持久化审计时，清理对应来源记录；新材料版本、重新获取来源仍清理旧记录。不同来源互不影响。
- 服务器操作可能仍在执行：首次刷新没有匹配成功并不表示旧请求已失败，不清理其标识；晚些时候的另一次刷新仍可恢复。达到 16 项上限时拒绝进一步请求并要求先读取材料，绝不静默淘汰可能仍会提交的旧 ID。
- 无自动重放、无服务端幂等保证，也不持久化请求标识到 localStorage。旧服务端不返回标识时继续原有保守状态转移行为。现阶段仅覆盖本机 Web 来源候选辅助，不代表 #72 Android/远程/真实模型整体验收。

## P2/P3 并发防护与恢复（PR #118 后续）

- 服务端在调用付费模型前，以草稿 ID + 来源 ID 为键登记当前执行；同一进程内再次请求相同来源立即返回 409 `EXTRACTION_IN_PROGRESS`，而不是在第二次模型调用结束后才检查 revision。旧客户端仅携带 revision 时同样受保护；不同来源可以独立执行。互斥结束后释放标记，审计仍通过现有事务提交。
- 受草稿访问权限保护的只读 `GET /drafts/{id}/sources/{source_id}/extraction-status` 返回 `active` 和草稿修订号，不暴露模型密钥、来源正文或具体操作标识。前端对有未确认请求的来源，重试前检查服务端活动；运行中拒绝重复触发付费请求。
- 重新读取材料时先确认活动状态，再读取持久化审计；匹配任一旧 `attempt_id` 时正常恢复 SUCCESS/PARTIAL/FAILED。未匹配且服务端确认闲置，则仅清理内存中的未确认标识，仍保留用户可见失败，不将旧 SUCCESS 升级为新成功。这样即使达到 16 条上限，服务端确认无活跃执行后仍可恢复重试。
- 并发防护状态为**单个正在运行的服务进程内**的活动表；它不是分布式锁或跨服务实例幂等保证。多工作进程共享数据目录的全局去重需额外架构支持。本次既不自动重放也不在 localStorage 持久化 ID；真实模型/Android/远程环境仍依 #72 单独验收。
