- **优先级**：必做（S2 核心支撑）
- **前置依赖**：[PT-010 #7](https://github.com/MrEcho114/PrivacyTrace/issues/7), [PT-301 #11](https://github.com/MrEcho114/PrivacyTrace/issues/11), [PT-503 #12](https://github.com/MrEcho114/PrivacyTrace/issues/12), [PT-709 #9](https://github.com/MrEcho114/PrivacyTrace/issues/9)

### 为什么做
真实商业 App 逻辑复杂且不可控，必须构建由自建源码编译、具有明确真实答案的受控 APK 场景，作为客观评测系统能力的基准。

### 做什么（输入与输出）
- **输入**：自建 Android 测试工程源码及配对的隐私政策文本。
- **输出**：
  1. 编译构建 6 至 8 个受控 APK 场景（可多个场景合并至少数 APK 中）：
     - 场景 1：申请权限但无敏感 API 调用；
     - 场景 2：存在敏感 invoke 调用且政策已做对应声明；
     - 场景 3：存在敏感 invoke 调用但政策未做声明；
     - 场景 4：政策中声明为上位数据类别（CATEGORY_MATCH）；
     - 场景 5：政策中包含否定描述（如“不收集通讯录”）但代码存在调用；
     - 场景 6：政策原文完整但抽取遗漏；
     - 场景 7：输入信息不全触发 partial 或证据不足；
     - 场景 8：Multidex 多包下的调用检出或解析失败容错；
  2. 固化每个场景的人工真值（Ground Truth）、预期状态与输入文件哈希；
  3. 保持测试工程源码与构建配置独立，避免同模板导致的数据泄漏。

### 完成标准（验收证据）
- 6 至 8 个受控场景均能通过系统适配器端到端运行并输出结构化报告；
- 既有的 35 个规则单测与本次新增的受控 APK 端到端测试计数分开统计，不互相混充；
- 测试工程源码与构建脚本齐备，可独立重复编译复现。

### 怎么检查（验证计划）
- 执行脚本完成编译并运行全链路分析；
- 比对系统输出状态与预设人工真值，统计匹配准确率；
- 验证异常场景下的容错输出。

### 这次不做
- 不在受控 APK 中加入自动联网发起真实请求的代码；
- 不使用未经验证的猜测性数据作为测试真值。
