## 二、技术工作与 AI 辅助边界

以下是对**项目工作内容**的说明，不是对每一行代码的生成者或所有设计决策来源的独立鉴定。

### 1. 现有工程与模块

- **Evidence／Privacy Taxonomy／Consistency Engine**：项目文档描述了证据建模、数据类型分类及多状态一致性核验；归属与设计决策可结合需求文档、关联 Issue、PR 和版本记录核对。
- **工程安全与规范**：包括 Docker 隔离执行、事实／声明／推断分离及报告措辞边界；实际约束须以代码及测试记录为准。
- **Code Review**：仓库保存多条 PR Review 与问题修复记录，可逐条列举已核实的审查内容；不笼统宣称“所有 PR 逐行由学生人工审查”。
- **项目管理**：GitHub Issues、PR、CI 配置等能够证明部分工程治理活动，但不能单凭提交者身份确定所有决策的独立性。

### 2. AI 使用记录与验证

- **代码实现辅助**：现有记录提及 FastAPI 接口逻辑、TypeScript 契约导出和测试骨架等。对外披露时应按具体文件、Commit 和实际使用工具复核，不预设 AI 只参与这几处。
- **自动生成文件**：[`scripts/export-schema.py`](../scripts/export-schema.py) 从模型导出 [`contracts.generated.ts`](../apps/web/src/contracts.generated.ts)；脚本确定性生成不等于文件每一行均由生成式 AI 撰写。
- **工程验证**：Ruff、pytest、Vitest、类型检查与构建用于检验对应版本的工程行为；检查通过不等于作者归属、原创性或国家标准合规性已获认证。
- **数据处理约束**：不应向未经批准的外部服务发送 APK、隐私政策原文、反编译代码、个人信息或凭据；历史上是否落实，应依据工具调用和运行记录核实，不作无依据的全周期保证。

## 三、贡献统计与真实性核验

### 1. Git 与 AI 归因是不同指标

- **Git 作者贡献**：Contributors／Commit 统计最多反映选定仓库范围与时间点的 Git 作者署名。合并提交、作者别名、机器人提交、共同作者以及外部生成内容都会影响解释。
- **待复算项**：此前草稿列有“489 次 Commit”、多名作者的分项次数与百分比；本修订**不将这些未经当前范围复算的数字作为已核定结果**。
- **统计复核口径**：未来如使用 Commit 数字，需记录冻结基准 SHA、目标分支、纳入的提交范围、别名合并依据、统计命令和复核人。修复前审查基线为 `c14364ee0f590929865cb9716d808750e4d5e47e`，**该 SHA 仅标识本轮修复起点，不代表已在该 SHA 完成全库统计**。
- **AI 辅助代码比例**：此前草稿中的“学生 35%–40%／AI 60%–65%”尚无可复现的逐文件归因和行数口径，因此**撤回精确比例**。Git 提交份额不能替代 AI 使用记录或代码来源审计。
- **人工贡献归属**：架构、规范、审查与管理等由团队承担的职责可以如实说明，但“100% 独立完成”等比例或排他性陈述，必须在成员、提交记录及工具使用日志支持后才能使用。

### 2. 复核所需证据

1. 各成员对真实职责与参赛身份的确认；GitHub Issue／PR／设计文档与 Commit 链接。
2. AI 使用清单（工具型号、调用日期、目的、输入／输出摘要、受影响文件和后续人工修改），避免写入敏感提示词或个人数据。
3. 若需要量化代码贡献，提供明确的计数单位、文件分类原则、生成文件处理方式、重叠贡献处理规则及可复现统计过程。
4. 实际参赛名单、指导教师审核和签署记录独立核实，不通过 CI 或 GitHub Contributors 自动推断。
